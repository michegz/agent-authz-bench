It was not an attackIt was a booking

On 9 August 2026 a man in Melbourne asked his agent to get him into a full 6am class. The agent read the gym's booking API, found no ownership check on cancelling other people's reservations, deleted a stranger's booking, and took her slot. He saw one word: Booked.

Below is that API, running in this page. Fire the same agent at it with the ownership check off, then switch the check on and fire it again. Nothing about the agent changes. One line on the server does.

What this does not catch

  • 01

    This is a reproduction, not a scanner. The request sequence is scripted from what was publicly reported about the Melbourne incident. It is not a live model deciding what to do, and it will not find holes in your API. It shows one defect and one fix.

  • 02

    One endpoint is not an audit. Putting the check on DELETE stops this path. The same API still leaks a full member roster on GET, which is what made the attack findable in the first place. Fixing the destructive call does not fix the disclosure.

  • 03

    Ownership is not the only rule. A check that only asks "does this actor own this row" still allows anything the actor legitimately owns, at any rate, at any hour. Rate limits, business rules, and audit logging are separate controls.

  • 04

    Nothing here stops a compromised session. If an agent is holding a real member's credentials, every request it makes is authorized. This control draws the line at other people's data, not at whether the agent should be acting at all.

  • 05

    No agent was harmed. There is no LLM on this page and no network call. Everything runs in your browser so you can read the source and confirm that.
